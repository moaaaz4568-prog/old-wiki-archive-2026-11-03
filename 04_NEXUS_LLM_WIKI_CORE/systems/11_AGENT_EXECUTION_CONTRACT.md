# 11 — عقد تنفيذ الوكيل لدورة المبيعات

## الغرض

توحيد ما يجوز للوكيل قراءته وكتابته وكيف يسلّم العمل، بحيث لا يخلط بين الترشيح
والاعتماد، ولا يتجاوز قواعد الويكي أو يعلن اكتمالًا غير مقاس.

## الصلاحيات والحدود

### مسموح

- قراءة `AGENTS.md`, `SCHEMA.md`, الأنظمة، التقارير، والأدوات ذات الصلة.
- قراءة `raw/` دون تعديل، والتحقق من البصمات والمواضع.
- الكتابة في مسار المهمة المصرح به، وسجلات staging/collections/checkpoints حسب الخطة.
- إنشاء Claims/Concepts/Master وفق SCHEMA فقط عندما تكون المهمة مخولة بذلك.
- تشغيل أدوات الفحص والاختبارات، وتسجيل stdout/exit code والزمن.

### ممنوع

- تعديل أو حذف أو نقل أي ملف في `raw/`.
- تعديل Claims أو Concepts أو Masters خارج قائمة المهمة.
- حذف دليل، رأي، تعارض، أو مصدر لأنه غير مريح.
- تسمية `processed` أو وجود Claim واحد «اكتمالًا».
- تحويل مثال أو رقم قصة إلى benchmark عام.
- الادعاء بتشغيل اختبار لم يُشغّل، أو ملء فجوة بقياس مخمّن.

## المدخلات

قبل التنفيذ، يتحقق الوكيل من وجود: الهدف، قائمة الملفات المسموح بها، النسخة/التاريخ،
نطاق المبيعات، SCHEMA، checkpoint السابق، وأمر الاختبار المتوقع. إذا كان أحدها
مفقودًا، يسجل `blocked` أو يعمل فقط في نطاق القراءة المأذون، ولا يخترع قيمة.

## المخرجات

كل تسليم يحتوي على:

1. الملفات المعدلة/المضافة ومساراتها الدقيقة.
2. ملخص التغيير وعلاقته بالمرحلة.
3. حقول SCHEMA التي أضيفت أو تحققت.
4. بوابات القبول ونتائجها.
5. أوامر الاختبار، exit code، وأي فشل قائم.
6. checkpoint يذكر ما هو مثبت وما هو غير مكتمل.
7. قائمة المخاطر أو `problem_id` إن ظهر إخفاق.

لا يكتب الوكيل chain-of-thought؛ يكتب أدلة قابلة للمراجعة وقرارات مختصرة.

## دورة التنفيذ الإلزامية

1. **Scope:** افحص المسارات وحالة git/الملفات قبل التعديل.
2. **Trace:** اربط المنتج بالمصدر، Claim، Concept، وMaster المناسب.
3. **Implement:** اكتب أقل تغيير يحقق العقد، مع الحفاظ على الملفات غير التابعة.
4. **Validate:** شغّل فحص schema والروابط والبصمات والاختبار الخاص بالمرحلة.
5. **Report:** اكتب التقرير في المسار المطلوب، ولا تخلط نتيجة العامل بقرار القائد.

## حالات التنفيذ

`planned` → `in_progress` → `validated` → `reported`.

الحالات البديلة: `blocked` (مدخل أو صلاحية ناقصة)، `failed` (اختبار أو بوابة فشل)،
`partial` (جزء مثبت مع حدود واضحة). لا ينتقل إلى `validated` مع اختبار غير منفذ؛
يظل `partial` أو `failed`.

## حالات الفشل

- فشل الصلاحية أو اتساع المسار: `blocked` مع مسار السبب.
- فشل schema أو التتبع: `failed`، مع منع تقرير نجاح.
- اختبار غير منفذ أو مخرجات ناقصة: `partial`، ولا يتحول إلى `validated`.
- تعديل خارج النطاق: حادث نطاق يجب إيقافه والإبلاغ عنه، لا إخفاؤه في التقرير.

## بوابات السلامة

- **A0 نطاق الكتابة:** كل diff داخل الملفات المصرح بها.
- **A1 عدم المساس بالخام:** بصمات raw قبل/بعد متساوية.
- **A2 schema:** الحقول المطلوبة والأنواع والحالات صحيحة.
- **A3 التتبع:** Claims لها source/locator، والروابط قابلة للحل.
- **A4 الصدق:** التقرير يذكر ما لم يُختبر أو لم يُحسم.

## معايير القياس

- نسبة الملفات المعدلة داخل النطاق = 100%.
- نسبة الاختبارات الموثقة بمخرجات فعلية = 100%.
- عدد ادعاءات الإكمال غير المدعومة = 0.
- معدل نجاح بوابات A0–A4.
- زمن التسليم من بدء المهمة إلى تقرير قابل لإعادة التشغيل.
