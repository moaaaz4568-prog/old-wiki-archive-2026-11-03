# 17 — عقد فهارس المجلدات والاسترجاع

**مراجعة:** 2026-10-10 — عقد ملاحة وتحقق، لا مخرجات معرفة.
**مراجع:** [13](13_MULTI_DOMAIN_ARCHITECTURE.md)، [05](05_RETRIEVAL_AND_EVALUATION.md)، [15](15_DOMAIN_COMPLETION_GATES.md).

## 1. الغرض والنطاق

- الفهرس يجيب: ماذا يفعل الملف؟ متى أقرأه؟ ما حالته؟ كيف أصل إلى دليله؟ وما الذي لا يغطيه؟
- كل مجلد تشغيلي أو معرفي مستخدم يحتاج `INDEX.md` محليًا؛ فهرس الأب لا يعوّضه.
- يشمل مجلدات المجالات وsubdomains والمصطلحات وClaims وConcepts وMasters ومجموعات القراءة.
- `raw/` استثناء immutable: فهرسته الخارجية في السجلات التشغيلية، لا إنشاء INDEX داخل الأصل.
- شجرة المصادر تبدأ `done/<domain>/<subdomain>/`؛ لا طبقة `source_refs` وسيطة.
- الفهرس لا يعوض النسخة المستقلة في done، ولا يُحسب مصدرًا أو Master أو دليلًا جديدًا.

## 2. رأس الفهرس المحلي

يلزم عنوان يعرّف وظيفة المجلد، `domain/subdomain` إن انطبقا، حد النطاق، وأماكن القراءة التالية.
يلزم تاريخ التحديث ونسخة catalog وsnapshot ومرجع الحالة في `config/processing_order.json`.
الفهرس يعرض حالة مشتقة؛ لا يملك `active_domain` مستقلًا ولا يرفع حالة ملف بمجرد إدراجه.
يصرّح بوجود pending أو partial أو stale دون تحويلها لغويًا إلى complete.
يوضح الفرق بين عدد المسارات، عدد البصمات الفريدة، وعدد المصادر المستقلة أدليًا؛ لا يساوي بينها.
إذا لم يفحص كل الملفات، يقول ذلك ويظهر المقام غير المفحوص؛ لا ينشر نسبة شاملة من عينة.

## 3. الحد الأدنى لكل مدخل

| الحقل | المعنى والفحص |
|---|---|
| `id`, `kind`, `path` | هوية مستقرة ونوع ومسار قابل للحل؛ يطابق سجل العنصر |
| `title`, `function` | وصف موجز غير عام يوضح سبب وجود الملف |
| `domain`, `subdomain`, `scope` | الملكية وما يدخل ويخرج؛ ليس تصنيفًا جديدًا من اسم الملف |
| `status`, `coverage_status` | الحالة الحقيقية ومرجعها؛ لا خلط route/source/domain_done |
| `snapshot_id`, `updated` | نسخة التغطية وزمن الفهرسة، لا ادعاء صلاحية المخزون الحالي |
| `upstream_refs`, `downstream_refs` | روابط الأدلة والمخرجات المستهلكة للعنصر |
| `retrieval_questions` | أسئلة يعرف الوكيل لماذا يفتح هذا الملف لأجلها |
| `limitations`, `conflict_refs` | الحدود والخلافات والفجوات دون إخفائها |

مثال metadata توضيحي لمدخل مصدر وُجه ولم يستخرج؛ ليس فهرسًا فعليًا:

```json
{
  "id": "SRC_EXAMPLE", "kind": "source_copy",
  "path": "done/sales/objection_handling/SRC_EXAMPLE.txt",
  "title": "مصدر توضيحي لاعتراض السعر",
  "function": "قراءة الدليل الأصلي المنسوخ مع تتبع route",
  "domain": "sales", "subdomain": "objection_handling",
  "scope": "حوار الاعتراض، لا تصميم السعر",
  "status": "route_done", "source_extraction_status": "not_started",
  "coverage_status": "partial", "snapshot_id": "SNAP_EXAMPLE",
  "upstream_refs": ["sources/SRC_EXAMPLE.md"],
  "downstream_refs": [],
  "route_ref": "done/sales/objection_handling/REF_SRC_EXAMPLE.json",
  "retrieval_questions": ["أين الدليل على سياق اعتراض السعر؟"],
  "limitations": ["لم يكتمل الاستخراج بعد"], "conflict_refs": [],
  "updated": "2026-10-10"
}
```

## 4. قواعد الرابط والعودة إلى الدليل

- metadata تحفظ مسارات نسبية إلى جذر الويكي وفق SCHEMA؛ روابط Markdown نسبية إلى ملف الفهرس.
- لا تنقل path من JSON إلى رابط Markdown دون حساب موقع الفهرس، وإلا ينكسر مسار متداخل.
- الفهرس العام → المجال → subdomain → سجل المصدر والنسخة → Claim وlocator → Concept → Master.
- يلزم المسار العكسي: Master إلى Concept/Claim ثم source_id وموضع الأصل، لا إلى ملخص فقط.
- روابط secondary تشير إلى المصدر نفسه؛ لا تخلق مصدرًا جديدًا ولا تزيد مقام الأدلة المستقلة.
- الحقول ذات المخرجات اللاحقة غير المبنية تبقى `[]`؛ لا روابط وهمية لإكمال الجدول.
- مسار قالب مثل `<domain>` يوضع داخل code block وموسوم مثالًا، لا رابطًا حيًا قابلًا للنقر.
- فحص anchors يتحقق من عنوان/معرف الوجهة نفسه؛ وجود الملف لا يكفي لإثبات fragment.

## 5. طريقة التحديث الآمنة

1. ثبّت snapshot وقائمة الملفات المأذون فهرستها؛ لا تجرد مجلدات خارج نطاق التكليف.
2. اجمع الحقول من المصدر المالك؛ عالج اختلاف الهوية/الحالة كfinding لا كتصحيح تخميني.
3. طابق العناصر على القرص بالمدخلات، وبيّن الملفات غير المفهرسة والروابط التي فقدت وجهتها.
4. اكتب وصف الوظيفة والأسئلة وحدود النطاق؛ قائمة أسماء فقط لا تفي بالعقد.
5. حدّث فهرس المجلد والأب ضمن الصلاحية، أو سلّم طلب تحديث للمالك؛ لا كتابة متزامنة لملف واحد.
6. شغّل فحص الروابط ومسارات الرجوع إلى الدليل، وسجل الأمر والنتيجة والنسخة في تقرير التحقق.
7. لا تغير حالة المجال؛ قدم نتيجة الفهرسة للمنسق وQA وفق [16](16_SEQUENTIAL_AGENT_ORCHESTRATION.md).

## 6. QA للفهرسة والاسترجاع

- كل ملف مطلوب في snapshot له مدخل وحيد واضح؛ aliases مراجع معلنة لا نسخ مكررة من نفس المخرج.
- وجود مدخل لا يثبت قراءة الملف: تحقق القراءة من سجل segments وملاحظات المراجعة، لا الفهرس.
- اختبر سؤال مفهوم واحد، وسؤال دمج، وسؤال خلاف، ومحاولة تعميم مثال، وخارج النطاق، ومعلومة متغيرة.
- سجل السؤال، الفهرس المستخدم، الملفات المسترجعة، Claim/locator، الإجابة، والحكم وأسبابه.
- قارن مع baseline بنفس الأسئلة والإعدادات؛ عدد الروابط أو الملفات ليس اختبار retrieval.
- المطلوب صفر رابط دليل مكسور وصفر ترقية حالة بلا سند وصفر إخفاء لخلاف مؤثر ضمن النطاق المفحوص.
- نقص الدليل يؤدي إلى امتناع صحيح؛ لا تستخدم Description الفهرس لملء فجوة معرفية.

## 7. أمثلة قبول ورفض وحدود التطبيق

- نسخة المصدر موجودة وroute صحيح، ولا Master بعد → فهرسة صادقة لحالة route_done، لا فشل.
- فهرس يسمي دفعة محدودة «كل مصطلحات المبيعات» → يرفض حتى لو كانت الروابط كلها سليمة.
- المصدر يخالف مصدرًا آخر → تظهر روابط الخلاف وحدود الرأيين، لا يحذف أحد المدخلين.
- metadata لمجال pending → يجوز فهرستها؛ لا تُكتب خلاصة Terms/Claims نيابة عن استخراجه.
- delta معلقة → توسم التغطية stale ويشار إلى سجلها وفق [19](19_NEW_SOURCE_REPROCESSING.md).
- هذا العقد لا ينشئ أو يحدّث فهارس المعرفة الآن؛ التنفيذ يحتاج تكليفًا منفصلًا وصلاحية.
