# 16 — تشغيل الأدوار وتسلسل المجالات

**مراجعة:** 2026-10-10 — عقد تنسيق لا إذن بتشغيل وكلاء الآن.
**مراجع:** [11](11_AGENT_EXECUTION_CONTRACT.md)، [15](15_DOMAIN_COMPLETION_GATES.md)، [18](18_DOMAIN_CATALOG_AND_PROCESSING_ORDER.md).

## 1. حدود التوازي والصلاحية

- يجوز intake عام لكل المجالات: الجرد، قراءة التصنيف، dedup، النسخة والفهرسة المرجعية.
- لا يسمح intake ببناء Terms/Claims/Concepts/Masters لمجال `pending` ولو أصبح `route_done`.
- يوجد مجال معرفي نشط واحد أو لا شيء؛ لا يوجد مجالان نشطان ولا مسار خلفي عبر المهارات.
- الأدوار وظائف، لا عددًا إلزاميًا من العمليات؛ تفويضها يحتاج إذن المهمة الحالية وقائمة ملفات صريحة.
- مهمة تصحيح الأنظمة الحالية بلا subagents وبلا بناء معرفة؛ لا يغير هذا العقد ذلك القيد.
- Codex غير مستخدم؛ العامل لا ينشئ تفويضًا فرعيًا من تلقاء نفسه.

## 2. سجل الحالة الوحيد

- الحالة التنفيذية في `config/processing_order.json` فقط، لا state منافسة في catalog أو checklist أو تقرير.
- يملك المنسق تحديث الحالة؛ العامل يسلم أدلة واقتراح انتقال ولا يرفع حالة المجال بنفسه.
- سجل checkpoint تاريخ للأحداث مربوط بـ`state_revision`، لا ملفًا ثانيًا يقرر `active_domain`.
- يستخدم الكاتب الوحيد قفلًا حصريًا وكتابة ذرية مع compare-and-swap على revision المتوقع.
- الاستبدال الذري مسموح لسجل الحالة المخوّل فقط؛ لا يبرر استبدال raw أو نسخة مصدر قائمة.

مثال حقول توضيحي لحالة مجمّدة، ليس قراءة أو تغييرًا للحالة الفعلية:

```json
{
  "schema_version": 1,
  "state_revision": 0,
  "catalog_revision": "example-v1",
  "order": ["sales", "outreach", "pricing_offers", "content_strategy"],
  "active_domain": null,
  "domain_states": {"sales": "pending", "outreach": "pending", "pricing_offers": "pending", "content_strategy": "pending"},
  "snapshot_refs": {},
  "gate_refs": {},
  "closure_refs": {},
  "pending_delta_ids": [],
  "lock": {"owner_run_id": null, "fencing_token": 0, "lease_until": null},
  "last_transition": null
}
```

`domain_states` يستخدم `pending|active|paused|blocked|done`؛ البوابات التفصيلية لها حالاتها في15.
`active_domain` يطابق مجال العمل المحتفظ بالقفل عند active/paused/blocked؛ التعليق وحده لا يحرره.
في handoff صريح يمكن أن يبقى مجال سابق paused بلا قفل وبلا كتّاب؛ يملك المجال المحدد في active_domain وحده حق الكتابة المعرفية.
حالة done تاريخية مرتبطة بـsnapshot؛ صلاحية التغطية الحديثة تقاس بالبوابات وdelta لا باسم الحالة وحده.
حقول `snapshot_refs/gate_refs/closure_refs` تربط الأدلة في ملفاتها، ولا تنسخ محتواها كمصادر حقيقة ثانية.

## 3. الأدوار وتسليماتها

| الدور | المدخل | التسليم وحد المسؤولية |
|---|---|---|
| المنسق | الحالة وcatalog وصلاحيات المهمة | snapshot وتوزيع الملكية والقفل، لا اعتماد معرفة بلا دليل |
| intake/classifier | مصادر عامة ثابتة | routes ونسخ ودليل التصنيف؛ لا استخراج pending |
| reader/extractor | مجال نشط + دفعة صريحة | segments ووحدات وcandidate terms/Claims معًا |
| reviewer | الأدلة ومرشحو الاستخراج | قرار لكل وحدة ومصطلح وClaim، وخلافات بلا حذف |
| concept author | Claims مراجعة | Concepts وحدودها؛ ليس انتظار كل المصطلحات لجمع دليل |
| master author | شهادة T شاملة + C/K لأدلته | كتاب متناسب واختبارات retrieval |
| QA/index | مخرجات مثبتة وفهارس | فحص مستقل وقرار hold/pass، لا توسيع صلاحيات الكتابة |

قد تتوازى دفعات داخل المجال النشط إذا أذن المنسق وفصل ملفاتها؛ لا كتابة مشتركة متزامنة لملف واحد.
الاستقلال في QA يعني مراجعًا غير مؤلف المخرجات؛ إن لم يتوفر يبقى الإغلاق blocked ولا يُدّعى QA مستقل.

## 4. عقد تكليف العامل

يلزم `run_id`, `role`, `domain`, `snapshot_id`, `batch_id`, `source_ids`, وحدود segments.
يلزم أيضًا `allowed_read_paths`, `allowed_write_paths`, `expected_state_revision`, `fencing_token`, ومعايير القبول.
يعلن العامل ما قرأه فعلًا، آخر segment، المخرجات، الفحوص وأكواد خروجها، والفجوات وما يحتاج تسليمًا.
غياب صلاحية أو مسار أو بوابة يسجل blocked؛ لا يخترع العامل config أو مخرجًا بديلًا خارج النطاق.
النسخة التاريخية لتكليف سابق لا تتقدم على تعليمات المستخدم الأحدث بالتوقف أو تضييق الملكية.

## 5. القفل والاستئناف

1. اقرأ الحالة وتحقق من schema ومن اتساق الترتيب مع catalog ومن عدم وجود domain ثانٍ نشط.
2. احصل على القفل أو انتظر؛ لا تفترض أن lease منتهية تعني موت الكاتب السابق.
3. استرداد القفل يحتاج إثبات توقف المالك ومراجعة الملفات الجزئية ثم زيادة `fencing_token` وrevision.
4. قبل كل تسليم كتابة، طابق domain وsnapshot وrevision وtoken؛ التسليم القديم يُرفض ولا يطغى على الأحدث.
5. عند انقطاع الجلسة، احفظ checkpoint آخر segment موثّق؛ لا تعتبر EOF أو انتهاء العملية إغلاقًا.
6. عند الاستئناف، أعد التحقق من بصمات المدخلات وdelta والبوابة المطلوبة، لا تعِد التشغيل الأعمى.
7. انتهاء مهمة فرعية يسلم عملها فقط؛ المنسق وحده يغير الحالة بعد التحقق.

## 6. الانتقال إلى المجال التالي

- يلزم `domain_done` على snapshot واضح، كل بوابات R/T/C/K/M/QA، وروابط وفهارس واختبارات استرجاع مثبتة.
- طابق cutoff مع سجل الوصول الجديد؛ كل delta لها أثر وقرار جدولة ظاهر وفق [19](19_NEW_SOURCE_REPROCESSING.md).
- delta مؤثرة غير مقيمة تمنع الانتقال؛ لا ينقل نجاح snapshot قديم تلقائيًا إلى آخر مخزون.
- أغلق تكليفات الكتابة القديمة، ثبت سجل الإغلاق، ثم حرر مجال العمل وفعّل التالي في معاملة حالة واحدة.
- تسجل المعاملة `from_domain`, `to_domain`, `closure_ref`, `delta_review_ref`, المراجع والوقت وrevision السابق والجديد.
- يمنع الانتقال عند عامل حي يكتب على snapshot القديمة أو QA غير مستقلة أو تغير مفاجئ في المصادر.

## 7. الاستثناءات واختبارات القبول

- مصدر pending يمكن نسخه وتصنيفه وفهرسته؛ طلب استخراج معرفته يفشل بفحص domain لا بعزل المصدر.
- source_done دون Master لا يمنع مواصلة بقية مصادر المجال؛ لا يعتمد reader على مخرج master author.
- T مكتملة لقسم واحد فقط → يمنع تكليف Master صغير حتى T المجال كله.
- عامل بمفتاح قفل قديم → يرفض التسليم ويُحفظ تقريره للتشخيص دون اعتماد.
- توقف المستخدم → تتوقف التكليفات ويثبت checkpoint؛ لا يُستنتج اكتمال أو إذن استمرار تلقائي.
- إعادة فتح مجال سابق لا تتم إلا بعد توقف العمل الآخر ومعاملة reopen صريحة؛ لا مجالين بالتوازي.
- نجاح فحص هذه الوثيقة ليس تنفيذًا للقفل ولا شهادة سلامة لأدوات لم تُختبر.
