# 13 — معمارية الويكي متعددة المجالات

**مراجعة:** 2026-10-10 — عقد تشغيلي؛ ليس إعلان تطبيق أو اكتمال معرفة.
**مرجع:** [الميثاق](../MULTI_DOMAIN_WIKI_OPERATING_CHARTER_2026-10-09.md)، [SCHEMA](../SCHEMA.md)، [المواءمة](../reports/sales-proof/MULTIDOMAIN_ALIGNMENT_2026-10-10.md).

## 1. الغرض وحدود السلطة

- يربط هذا النظام التوجيه والاستخراج والتوليف والاسترجاع دون خلط حالات إغلاقها.
- النطاق أربعة مجالات: `sales`، `outreach`، `pricing_offers`، `content_strategy`.
- التصنيف الأولي عام لكل المجالات؛ صناعة المعرفة في مجال نشط واحد فقط.
- `config/domain_catalog.json` يملك تعريف النطاق؛ `config/processing_order.json` يملك الحالة والترتيب والقفل.
- أمثلة JSON هنا عقود حقول توضيحية، لا سجلات حقيقية ولا تعليمات بإنشائها الآن.

## 2. الطبقات والمنتج والمستهلك

| الطبقة | المنتج ومسؤوليته | المستهلك وما يتحقق منه |
|---|---|---|
| الأصل في `new/` أو `raw/` | الاستقبال يثبت الهوية دون تغيير الأصل | التوجيه يتحقق من SHA-256 وثبات البايتات |
| `sources/` | سجل Source وفق SCHEMA | الاستخراج يحل `source_id` والمسار والبصمة |
| `done/<domain>/<subdomain>/` | نسخة مستقلة متحققة مع route/reference metadata | القراءة تعود لنفس المصدر، لا لدليل مستقل جديد |
| `collections/<domain>/` | snapshots وسجل المرشحين والتغطية | بوابات R/T/C تقيس المقام الحقيقي |
| سجل المصطلحات | terms مع التعريف والسياق والمواضع والمراجعة | Concepts تميز المعنى لا مجرد التشابه اللفظي |
| `claims/` | candidate Claims أثناء القراءة ثم المراجعة | Concepts تستخدم الأدلة المراجعة وحدودها |
| `concepts/` | شرح الآلية والشروط والخلافات | Masters تجمع القرارات دون نسخ الصفحات |
| `masters/` | كتب معرفية بعد بوابة المجال T | الاسترجاع يختبر القرار والإحالة والامتناع |
| `INDEX.md` | وصف وظائف الملفات ومساراتها وحالتها | الوكيل يختار الملف ويعود إلى الدليل |

المسارات الفرعية للقراءة والمصطلحات تُسجل في snapshot؛ لا يُخترع جذر معرفة موازٍ.
الفهارس والتقارير مشاهد مشتقة من السجلات وليست سجل حالة ثانٍ أو دليلًا مستقلًا.

## 3. دورة العمل بلا اعتماد دائري

1. intake: جرد عام وتصنيف دلالي وdedup ونسخة متحققة، بما في ذلك المجالات `pending`.
2. تثبيت snapshot شامل للمجال النشط من كل مرشحي cutoff وقراراتهم، وفق [15](15_DOMAIN_COMPLETION_GATES.md).
3. القراءة الاستخراجية: جمع candidate terms وcandidate Claims معًا، مع مواضعها وسياقها.
4. مراجعة الوحدات المكتشفة واستكمال الأجزاء الناقصة؛ لا انتظار T لكتابة الاقتباس أو مراجعته.
5. مراجعة Concept بعد Claims التي يستند إليها؛ اعتماد المصطلح وحده لا يثبت الآلية.
6. `domain_terms_complete` بعد كافة مصادر وأقسام snapshot، قبل بدء أي Master حتى المتخصص الصغير.
7. Masters المطلوبة والاسترجاع والفهارس ثم QA مستقل؛ بعدها فقط `domain_done` وانتقال المجال.

`route_done` لا يعني `source_done`؛ وجود النسخة داخل done لا يرفع أي بوابة معرفية.
`source_done` يعني استخراج جميع وحدات محتوى المصدر ومراجعتها، ولا يحتاج Concept أو Master.
قد تُستكمل مساهمات subdomain قبل المصدر متعدد المجالات كله؛ لا تُسمى هذه `source_done` عامة.
إذا بقيت وحدات لمجال `pending` فهي إحالات انتظار ظاهرة، ويظل اكتمال المصدر الكلي جزئيًا.
تُقاس بوابات المجال بمساهماته الكاملة في كل مصدر، لا باشتراط استخراج مجال آخر قبله.

## 4. عقد المصطلح

يلزم لكل مصطلح مرشح: هوية مستقرة، لفظ المصدر، الاسم القياسي، تعريف أو فجوة تعريف، نطاق، ومواضع.
هذه امتدادات سجل المصطلحات؛ لا تضيف قيمًا إلى `Claim.status` أو `Source.status` في SCHEMA.

```json
{
  "term_id": "TERM_EXAMPLE_001",
  "domain": "sales",
  "subdomain": "objection_handling",
  "snapshot_id": "SNAP_EXAMPLE",
  "source_label": "اعتراض السعر",
  "canonical_label": "اعتراض السعر",
  "aliases": [],
  "definition": null,
  "definition_gap": "يلزم استكمال التعريف من سياق المصدر",
  "scope": "حوار مع مشترٍ يعترض على السعر، لا تصميم نموذج السعر",
  "occurrences": [{"source_id": "SRC_EXAMPLE", "locator": "line 3-4", "segment_id": "SEG_1"}],
  "claim_refs": ["CLM_EXAMPLE_001"],
  "status": "candidate",
  "review": {"reviewer": null, "decision": "pending", "reason": null},
  "merge_target": null,
  "concept_refs": [],
  "master_refs": []
}
```

- لا تُملأ `definition` بالتخمين؛ الفجوة الجوهرية تمنع T حتى تُراجع ويُحسم مصيرها.
- حالات المصطلحات: `candidate` ثم `reviewed` أو `merged` أو `rejected` مع سبب ومراجع.
- الدمج يربط `merge_target` ويحفظ الألفاظ والمواضع؛ تشابه الاسم لا يبرر دمج معنيين مختلفين.
- `claim_refs` يجوز أن تتضمن مرشحين أثناء القراءة؛ يجب مراجعة المستخدم منها قبل التوليف.
- `concept_refs` و`master_refs` يجوز أن يبقيا فارغين عند اكتمال الاستخراج، ويُربطان لاحقًا.

مرشح Claim يكتب في اللحظة نفسها، لا بعد T؛ المثال التالي يوضح الحقول لا اقتباسًا فعليًا:

```json
{
  "type": "claim", "claim_id": "CLM_EXAMPLE_001",
  "statement": "صياغة مقيدة بما يقوله الاقتباس الفعلي",
  "source_id": "SRC_EXAMPLE", "locator": "line 3-4",
  "evidence_quote": "حقل توضيحي يستبدل بالاقتباس الحرفي عند التنفيذ",
  "evidence_type": "example", "confidence": "source_reported",
  "scope": "سياق المثال وقناته وشروطه وحدوده",
  "what_it_does_not_prove": "لا يثبت قاعدة عامة",
  "status": "candidate", "created": "2026-10-10", "updated": "2026-10-10",
  "review": {"reviewer": null, "decision": "pending", "review_ref": null}
}
```

## 5. وحدة المحتوى والمحاسبة

- ليست الوحدة «Claim واحد لكل ملف»؛ تشمل التعريف، الشرط، الخطوة، النتيجة، الرقم، المثال، الرأي والحد.
- لكل segment إحالات `content_unit_ids` إلى قائمة `content_units`؛ لكل وحدة `unit_id` و`locator` و`term_ids` و`claim_ids` و`disposition` و`review_ref`، والقوائم غير المنطبقة فارغة.
- لكل وحدة مصير: مستخرجة ومراجعة، مكررة مع رابط أصلها، ليست معرفية مع سبب، أو إحالة لمجال آخر.
- إحالة مجال آخر ليست استخراجًا له ولا استبعادًا صامتًا؛ تربط نفس هوية المصدر وموضع الوحدة.
- الفجوة غير المراجعة أو المحتوى غير المقروء يبقيان الحالة مفتوحة مهما كثرت Claims الأخرى.
- كل occurrence يحفظ اقتباسه أو رابط دليل قابل للحل؛ بصمة النسخ لا تُحتسب أدلة مستقلة.

## 6. توافق المراجعة والتوليف

- تُحفظ حقول SCHEMA وحالاته؛ ملحق التوجيه منفصل عن `Source.status` القديم.
- Claims تستخدم `status: reviewed` مع `confidence: disputed` عند خلاف مراجع؛ لا `status: disputed` غير المعرّف.
- Concept قد يبقى `disputed` وفق SCHEMA مع عرض الأدلة والشروط، ولا يساوي ذلك فشل التتبع.
- الخلاف المدعوم لا يُحذف، ولا تُشترط تسوية الآراء لاجتياز مراجعة أمينة.
- المرجع العام للأدلة [02](02_CLAIM_EXTRACTION.md)، وللمفاهيم [03](03_CONCEPT_AUTHORING.md)، وللتوليف [04](04_MASTER_AUTHORING.md).
- لا ينسخ هذا النظام أدوات المبيعات إلى مجال آخر بلا تكييف نطاقها؛ تفاصيل [18](18_DOMAIN_CATALOG_AND_PROCESSING_ORDER.md).

## 7. اختبارات القبول وحدود المهمة

- إذا وُجه مصدر outreach أثناء sales، تمر R المحلية وتبقى كتابة معرفته مقفلة.
- إذا راجعت كل وحدات مصدر، يجوز `source_done` مع `master_refs: []`؛ لا اعتماد دائري.
- إذا اكتمل قسم وبقي مصدر صالح لم يُقرأ في قسم آخر، تُرفض T وأي Master جديد.
- إذا ظهر خلاف مدعوم، يحفظه Concept وMaster باختبار استرجاع لا بتوحيد قسري.
- إذا جاءت delta، تحفظ الأدلة القديمة وتراجع الصلاحية وفق [19](19_NEW_SOURCE_REPROCESSING.md).
- نشر هذه العقود لا ينشئ snapshots أو مصادر أو معرفة، ولا يمنح أي بوابة PASS.
