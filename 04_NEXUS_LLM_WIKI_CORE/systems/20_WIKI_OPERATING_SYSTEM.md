# 20 — نظام تشغيل الويكي من الطلب إلى التسليم

**المراجعة:** 2026-10-18 — عقد تشغيل موحّد؛ لا يثبت وحده تشغيل أي دفعة أو اكتمال أي مجال.  
**النوع:** مواصفة تنسيق وقرار وتتبّع.  
**المرجع:** [AGENTS](../AGENTS.md)، [SCHEMA](../SCHEMA.md)، [13](13_MULTI_DOMAIN_ARCHITECTURE.md)–[19](19_NEW_SOURCE_REPROCESSING.md)، و`config/processing_order.json`.

> هذه الوثيقة تصف ما يجب تسجيله وما الذي يفتح كل انتقال. لا تطلب من النموذج كشف تفكير داخلي أو سلسلة خواطر؛ المطلوب هو القرار النهائي، والدليل القابل للفحص، وحدود القرار.

## 1. الغرض والحدود

يحول هذا النظام طلبًا أو تغييرًا إلى تسليم قابل لإعادة الفحص. يفصل بين:

1. فهم الطلب وتثبيت الصلاحية.
2. تنفيذ المخرج داخل مسارات وملفات مملوكة صراحةً.
3. مراجعة الأدلة والبوابات.
4. تسليم حالة صادقة، مع إبقاء `blocked` و`partial` و`stale` ظاهرة.

لا يستبدل هذا النظام `config/processing_order.json`، ولا يرفع حالة مجال، ولا يحوّل وجود ملف أو تقرير إلى دليل اكتمال. يظل `raw/` غير قابل للتعديل، ويظل المجال المعرفي النشط واحدًا فقط. يسمح الاستقبال العام بالتوجيه لمجال `pending`، لكنه لا يفتح استخراج Terms/Claims/Concepts/Masters له.

## 2. المدخلات والمخرجات والمالك

### 2.1 المدخلات الإلزامية

| المدخل | ما يجب التحقق منه | المالك المرجعي |
|---|---|---|
| طلب المستخدم أو تكليف Commander | النطاق، الملفات المسموحة، الموعد أو سبب التوقف، وما لا يجوز تغييره | Commander |
| `AGENTS.md` و`SCHEMA.md` | قواعد المصدر والحقول والحالات | منسق التشغيل |
| `systems/INDEX.md` | ترتيب القراءة والروابط الوظيفية | منسق التشغيل |
| الميثاق ومواءمة الموجة | آخر قرار حاكم عند التعارض | Commander |
| الأنظمة 13–19 | العقد المتخصصة للتوجيه والبوابات والتسلسل والتغيير | مالك النظام المعني |
| `config/domain_catalog.json` و`config/processing_order.json` | المجال النشط، الترتيب، القفل، ونسخة catalog | Commander؛ قراءة العامل فقط |
| المدخلات الفعلية والـsnapshots والـcheckpoints | الهوية والبصمات والنطاق السابق والحالة الحالية | مالك المخرج |

إذا غاب مدخل حاكم أو تعذر حل تعارضه، تكون النتيجة `blocked` ولا يُستبدل المدخل بتخمين أو بذاكرة النموذج.

### 2.2 المخرجات الإلزامية

كل تشغيل يخرج، بقدر النطاق المأذون، ما يلي:

- `workflow_record` يحدد `workflow_id`, `kind`, `domain`, `snapshot_id`, `source_ids`, `status`, و`evidence_refs`.
- `decision_ledger` يسجل القرارات الانتقالية ومراجعها، لا سلسلة التفكير الداخلية.
- مخرجات المهمة نفسها في المسارات المسموحة، مع روابط رجوع إلى الدليل.
- سجل فحوص يذكر الأمر/الأداة، النتيجة، وقت التنفيذ، والمسار أو العينة المفحوصة.
- `checkpoint` عند كل وحدة قابلة للاستئناف.
- تسليم نهائي يذكر الحالة، المقام والبسط إن كانا مقاسين، الفجوات، والأسباب التي تمنع أي ادعاء أوسع.

وجود المخرج لا يساوي نجاح البوابة. لا يكتب العامل حالة `domain_done` أو يغيّر القفل؛ يقدم أدلة واقتراح انتقال، ويملك Commander معاملة الحالة.

### 2.3 الملكية

| الدور | يملك | لا يملك |
|---|---|---|
| Commander/المنسق | `processing_order.json`، القفل، ترتيب المجالات، قرار الانتقال، تفسير التعارضات الصلاحية | اختراع دليل أو اعتماد مخرج بلا فحص مستقل |
| Worker | الملفات المسندة وسجل التشغيل داخل `allowed_write_paths` | `raw/`، config، ملفات عامل آخر، أو مجال pending معرفيًا |
| Reviewer | سجل المراجعة وقرار القبول/الرفض وأسباب الفجوة | إعادة كتابة دليل خام أو اعتبار رأيه مصدرًا |
| Concept/Master author | مخرجات التوليف ضمن صلاحية المجال وبعد بواباتها | تجاوز T أو إضافة حقائق بلا Claims مراجعة |
| QA/index | فحوص مستقلة، الروابط، الاسترجاع، وسجل hold/pass | توسيع النطاق أو إخفاء finding |

إذا لم تكن الملكية واضحة في التكليف، لا تبدأ الكتابة؛ أنشئ finding `ownership_missing` في سجل القرار ثم توقف.

## 3. ترتيب القراءة قبل أي قرار

يقرأ المنفذ بالترتيب التالي، ويسجل في `workflow_record.read_refs` ما قرأه فعلًا:

1. تعليمات المستخدم الحالية وحدود المسارات.
2. `../AGENTS.md` ثم `../SCHEMA.md`.
3. `systems/INDEX.md` لاختيار النظام الأقرب، دون اعتباره سجل حالة.
4. الميثاق المصحح ومرجع المواءمة الأحدث عند وجود تعارض.
5. النظام 20، ثم النظام المتخصص من 21–25، ثم 13–19 ذات الصلة.
6. `config/domain_catalog.json` و`config/processing_order.json` قراءةً فقط، والتحقق من `current_domain` و`current_domain_status` و`strict_order`.
7. السجلات الفعلية: Source، manifest، snapshot، coverage، Claims/Concepts/Masters، الفهارس، delta، والـcheckpoint المطلوبة.
8. المدخل الأصلي أو النسخة المتحققة، بالمسار والبصمة والـlocator، قبل كتابة أي ملخص.

لا يجوز عكس الترتيب بأن يُستنتج النطاق من Master قديم أو من اسم الملف قبل قراءة متن المصدر. لا يثبت `EOF` أو عدّ الملفات القراءة الدلالية.

## 4. حدود الصلاحية والقراءة والكتابة

### 4.1 قواعد غير قابلة للتفاوض

- يجب أن يكون كل مسار قراءة أو كتابة نسبيًا أو معرفًا في التكليف؛ لا `..` ولا مسار غير مسند.
- MUST NOT يُعدّل أو يُنقل أو يُعاد تسمية أو يُحذف أي ملف في `raw/`.
- MUST NOT تُنشأ نسخة ثانية لمصدر واحد لمجرد وجود مسار ثانوي؛ الهوية والبصمة تحددان المصدر.
- يجوز للتوجيه العام قراءة وتصنيف ونسخ مصدر `pending`، لكن لا يجوز استخراج معرفته قبل فتح مجاله رسميًا.
- لا يوجد مجالان معرفيان نشطان؛ `route_done` لا يساوي `source_done` ولا `domain_done`.
- كل Claim أو تعريف أو قرار استرجاع يجب أن يعود إلى دليل وموضع أو يوسم صراحةً كفجوة/استنتاج/فرضية.
- التقرير أو الفهرس مشهد مشتق؛ لا يملك الحالة بدل config ولا يرفع بوابة.
- لا تُصلح مشكلة خارج النطاق في نفس التشغيل؛ تسجل كـ`out_of_scope_finding` مع المالك المقترح.

### 4.2 أولوية الأوامر عند التعارض

1. طلب المستخدم الحالي فيما يخص التوقف أو تضييق النطاق.
2. سلامة المصدر وimmutability.
3. `SCHEMA` والـenums الثابتة.
4. `processing_order` كحالة وترتيب وقفل.
5. الأنظمة 13–19 والأنظمة 20–25 كإجراءات تنفيذية.
6. الفهارس والتقارير التاريخية كمراجع، لا كسلطة حالة.

إذا تعارضت صلاحيتان، لا يحاول العامل الدمج الصامت؛ يسجل `authority_conflict` ويطلب قرار Commander.

## 5. آلة الحالات الموحدة

هذه حالات سير عمل عامة، وتبقى حالات Source وGate وDomain كما يحددها `SCHEMA` والـconfig. الحالة النهائية للعمل لا تعني إغلاق المجال.

```text
received
  -> scoped
  -> inputs_verified
  -> plan_locked
  -> in_progress
  -> evidence_ready
  -> review_pending
  -> gates_pending
  -> delivered

أي حالة عمل -> blocked | failed | paused | stale
blocked/paused -> resumed فقط بعد إزالة السبب وتثبيت checkpoint
stale -> impact_review -> in_progress أو blocked
failed -> recovery_classified -> retry أو blocked
```

| الحالة | شرط الدخول | ما يسمح به | ما يمنعه |
|---|---|---|---|
| `received` | وصل طلب أو تكليف بمعرف | تسجيله فقط | الكتابة المعرفية |
| `scoped` | ثبتت الملفات والمالك والهدف | إعداد خطة القراءة | توسيع النطاق |
| `inputs_verified` | حُلّت الهوية والبصمة والنسخ والـconfig | التخطيط القابل للتنفيذ | استخدام مدخل غير قابل للتحقق |
| `plan_locked` | ثبتت gates السابقة ومسارات الكتابة | تنفيذ الخطوات المسندة | تغيير الخطة بلا decision ledger |
| `in_progress` | بدأ عامل مملوك على snapshot/batch | كتابة المخرجات الجزئية وcheckpoint | كتابة مشتركة غير مقفلة |
| `evidence_ready` | كل مخرج له evidence refs وcoverage | تسليمه للمراجع | تسميته قبولًا نهائيًا |
| `review_pending` | سلم العامل معايير القبول | مراجعة مستقلة | أن يراجع المؤلف نفسه كـQA مستقل |
| `gates_pending` | مخرجات المراجعة موجودة | تشغيل البوابات المطلوبة | إعلان PASS قبل الأدلة |
| `delivered` | اكتملت فحوص المهمة ونُشر التسليم | إبلاغ Commander بالحالة | ادعاء `domain_done` بلا إغلاقه |
| `blocked` | مانع معروف قابل للتتبع | حفظ الأدلة والانتظار | الاستمرار بالتخمين |
| `failed` | فشل تنفيذ أو سلامة أو عقد | تصنيف failure وrecovery | retry أعمى |
| `paused` | توقف مأذون أو قفل محتجز | checkpoint وتسليم جزئي | إعلان اكتمال |
| `stale` | delta أو تغير snapshot/مصدر/نطاق | invalidation وتقدير أثر | استخدام دليل قديم كحديث |

انتقالات البوابات المتخصصة هي `R → T → C → K → M → QA` ضمن شروطها؛ لا يُفهم ترتيب الحالات العامة على أنه إذن لتجاوز بوابة متخصصة.

## 6. سجل القرار (Decision Ledger)

### 6.1 الغرض

السجل هو دفتر قرارات قابل للفحص، وليس مساحة لتفريغ التفكير الداخلي. يكتب الخلاصة التشغيلية: السؤال، القرار، الأدلة، حدود الصلاحية، وما سيحدث بعده.

### 6.2 الحد الأدنى للسجل

```yaml
decision_id: DEC_20261018_example_001
workflow_id: WF_20261018_example
recorded_at: 2026-10-18T10:00:00Z
actor: worker|reviewer|commander|qa
scope: source|batch|subdomain|domain|system-docs
question: هل يجوز الانتقال إلى المرحلة التالية؟
decision: لا، الحالة blocked
evidence_refs:
  - READ_EXAMPLE
  - GATE_T_EXAMPLE
authority_ref: systems/15_DOMAIN_COMPLETION_GATES.md#4
state_before: review_pending
state_after: blocked
blockers:
  - unresolved_candidate_membership
next_action: يراجع Commander المرشح قبل إعادة تقييم T
status: recorded
```

`decision` و`next_action` موجزان وقابلان للاقتباس. لا يلزم ولا يُطلب تسجيل سلسلة خواطر أو بدائل داخلية غير قابلة للفحص؛ إذا رُفض بديل، يكفي ذكر سبب تشغيلي ومصدره مثل `violates_gate:T`.

### 6.3 قواعد الكتابة

- يسجل القرار فور صدوره، لا في نهاية الجلسة من الذاكرة.
- كل انتقال يذكر الحالة السابقة والجديدة وrevision أو fencing token إن كان متعلقًا بـconfig.
- كل `pass` يضم دليلًا ومراجعًا ومراجعًا وتاريخًا؛ كل `blocked` يضم سببًا قابلًا للإزالة أو يوسم `external_dependency`.
- لا يمحو السجل عند retry؛ يضيف سجلًا جديدًا ويربطه بـ`supersedes` أو `retry_of`.
- إذا تغير الدليل، يسجل `stale` و`delta_id` بدل تعديل القرار القديم.

## 7. البوابات العامة

| البوابة | سؤالها | دليل المرور | أسباب التوقف النموذجية |
|---|---|---|---|
| `S0` النطاق والصلاحية | هل المهمة والمالك والمسارات واضحة؟ | تكليف كامل وقراءة مرجعية | ملف غير مملوك، تعارض تعليمات، مجال ثانٍ |
| `R` التوجيه/المصدر | هل الهوية والقراءة والنسخة والمسار متحققة؟ | manifest، hash، coverage، route، copy checks | raw متغير، مسار غامض، فشل نسخة |
| `T` المصطلحات | هل كل مصطلحات snapshot الشاملة لها مصير وتعريف متتبع؟ | snapshot كاملة + term review | مرشح جوهري بلا قرار، subdomain ناقص |
| `C` الادعاءات | هل كل Claim ذري ومراجع بموضع ونوع ونطاق؟ | quote/hash/locator/review | اقتباس غير مطابق، تعميم مثال، Claim معلّق مستخدم |
| `K` المفاهيم | هل كل Concept مبني على Claims مراجعة ويعرض حدوده؟ | concept refs + conflict/limits | فجوة دليل، آلية غير مدعومة |
| `M` الماستر/الاسترجاع | هل بدأ بعد T وله dependencies واختبارات retrieval؟ | Master + retrieval trace | T stale، Master جزئي مطلوب، سؤال بلا trace |
| `QA` الإغلاق | هل فحص مستقل التغطية والروابط والـdelta؟ | QA record، baseline، indexes | QA غير مستقل، روابط مكسورة، delta غير مقيمة |

لا يكفي نجاح بوابة واحدة لإعلان التسليم النهائي. يمكن أن يكون مصدر `source_done` بلا Master، ويمكن أن تكون الوثيقة الجديدة `delivered` بلا `domain_done`.

## 8. خطوات التنفيذ الموحدة

1. أنشئ `workflow_id` ثابتًا وسجل حدود التكليف.
2. اقرأ المراجع بالترتيب أعلاه، وسجل `read_refs` وما لم يُقرأ عند الحاجة.
3. تحقق من صلاحية المسارات والمالك والمجال النشط وrevision والقفل.
4. ثبّت المدخلات: source IDs، snapshot، hashes، cutoff، والـbatch/segments.
5. أنشئ decision ledger وخطة قصيرة تربط كل خطوة ببوابة ومخرج.
6. نفذ أصغر وحدة قابلة للإعادة، واحفظ checkpoint بعد كل مصدر/segment/سجل.
7. افصل القياسات: سلامة IO، التغطية الدلالية، عدد الوحدات، وحالة المراجعة.
8. سلّم المخرج للمراجع مع فحوص النجاح والفجوات؛ لا تمنح نفسك QA المستقل.
9. شغّل البوابات في نطاقها الصحيح، ثم حدّث ledger والتقرير.
10. أبلغ Commander بالحالة الفعلية فقط؛ لا تغير config إلا بتكليف يملك ذلك.

## 9. فحوص النجاح

يكون التسليم ناجحًا في نطاقه إذا تحققت جميع النقاط التالية:

- كل ملف أنشئ أو عُدّل داخل `allowed_write_paths`، ولا ملف خارج نطاق المستخدم تغيّر.
- كل رابط داخلي مذكور في التسليم قابل للحل، وكل مرجع دليل يحدد Source/Claim/locator أو يصرح بالفجوة.
- لا يوجد انتقال حالة بلا predecessor أو gate evidence.
- `raw_changed=0` عند وجود مصدر خام في النطاق.
- كل عدد له مقام وبسط ومصدر قياس، أو يوسم `unknown/not_measured`.
- الفشل أو التوقف مسجل في `decision_ledger` وcheckpoint، وليس مخفيًا خلف كلمة `done`.
- إذا كانت المهمة معرفية، تطبق فحوص 21–23؛ وإذا كانت handoff أو update، تطبق 24 أو 25 أيضًا.

نجاح أداة بنيوية مساعدة مثل `tools/wiki_quality.py` لا يثبت القراءة الدلالية أو T/C/K/M/QA ما لم يذكر verifier ذلك صراحةً.

## 10. أسباب التوقف القياسية

| الرمز | السبب | الإجراء |
|---|---|---|
| `scope_missing` | لا يوجد تكليف أو مسارات أو مالك واضح | blocked، اطلب عقدًا محددًا |
| `authority_conflict` | تعارض بين المستخدم/config/وثيقة حاكمة | blocked، decision Commander |
| `active_domain_conflict` | محاولة معرفة مجال ثانٍ | blocked، لا تخلط القفل |
| `raw_integrity_failure` | تغير/فقد/فشل hash | quarantine أو delta، لا تعديل الأصل |
| `coverage_gap` | segments أو وحدات غير مغطاة | partial/blocked حتى تسوية الفجوة |
| `missing_evidence` | Claim/Concept/Master بلا trace | لا تكتب أو لا تعتمد |
| `gate_not_passed` | predecessor بوابة غير ناجحة | ارجع للمرحلة السابقة |
| `stale_delta` | مصدر/نطاق/وثيقة تغيرت | invalidation وفق25 |
| `review_unavailable` | لا يوجد Reviewer مستقل | hold، لا QA مستعار |
| `tool_limit` | الأداة لا تثبت الادعاء المطلوب | سجل الحد واستعمل فحصًا مناسبًا أو امتنع |

## 12. معيار التسليم الصادق

صيغة التسليم الدنيا:
