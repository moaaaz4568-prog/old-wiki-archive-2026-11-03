# 19 — وصول مصدر جديد وإعادة المعالجة

**مراجعة:** 2026-10-10 — عقد delta/invalidation، لا تشغيل مصادر.
**مراجع:** [14](14_SOURCE_ROUTING_AND_DONE_TREE.md)، [15](15_DOMAIN_COMPLETION_GATES.md)، [16](16_SEQUENTIAL_AGENT_ORCHESTRATION.md).

## 1. الضمانات

- كل وصول جديد أو اكتشاف مرشح متروك أو تغير نطاق catalog له delta صريحة قابلة للتتبع.
- snapshot القديمة وأدلة إغلاقها لا تُمحى ولا تُنسب تلقائيًا إلى أحدث مخزون.
- التغطية الأحدث للمجال المتأثر تصبح `stale` إلى أن يُراجع أثر delta، حتى لو كان المجال done تاريخيًا.
- لا `reopen` صامت ولا مجالين معرفيين نشطين؛ المرور في intake لا يغير القفل التسلسلي.
- الأصل ثابت؛ نسخة معدلة لاحقًا مصدر جديد بمعرف وبصمة جديدين، لا تعديل الملف القديم في raw.
- duplicate بالبصمة وصول مسار جديد لا دليل جديد؛ لا يُستخرج ثانية كمصدر مستقل.

## 2. المدخلات وسجل delta

يلزم هوية الحدث ووقت الاكتشاف والمسار والبصمة، snapshot السابقة، والمجالات/المخرجات المحتمل تأثرها.
عدم معرفة مجال المصدر يبقي تقييم الأثر مفتوحًا؛ لا يصنف الحدث تلقائيًا «غير مؤثر».
المثال التالي حدث مصطنع غير مقيّم، وليس إعادة فتح أو مصدرًا فعليًا:

```json
{
  "delta_id": "DELTA_EXAMPLE_001",
  "event_type": "new_source",
  "discovered_at": "2026-10-10T12:00:00Z",
  "candidate_id": "ITEM_EXAMPLE", "source_id": "SRC_EXAMPLE",
  "source_path": "new/example.txt", "content_hash": "sha256:<64-hex>",
  "previous_snapshot_id": "DOMAIN_SNAPSHOT_EXAMPLE",
  "discovered_before_previous_cutoff": false,
  "affected_domains": ["sales"],
  "secondary_domains": [],
  "duplicate_of": null,
  "impact_status": "pending_review",
  "coverage_status": "stale",
  "invalidated_gates": ["R", "T", "C", "K", "M", "QA"],
  "affected_refs": [], "impact_reason": "لم تُقيّم الوحدات الجديدة بعد",
  "reviewer": null, "review_ref": null,
  "schedule": "queued", "reopen_decision_ref": null,
  "next_snapshot_id": null, "expected_state_revision": 0
}
```

`event_type` يكون `new_source|exact_duplicate|source_revision|missed_candidate|catalog_change|evidence_correction`.
`affected_refs` تربط Terms/Claims/Concepts/Masters والفهارس المتأثرة بعد المراجعة، لا تُملأ بالتخمين.
فراغ affected_refs قبل المراجعة لا يعني عدم الأثر؛ invalidation تحفظ التحفظ حتى القرار المدعوم.

## 3. استقبال وتقدير الأثر

1. سجل الحدث فورًا مع cutoff القديمة، ولا تُدخل المصدر في لقطة مغلقة بتغيير تاريخها.
2. نفذ intake العام: فحص الأصل والقراءة الدلالية للتصنيف وdedup وverified copy وroute metadata.
3. راجع primary/secondary والمساهمات المتأثرة؛ لا تستخرج معرفة pending أثناء التقدير.
4. فرق بين وصول بعد cutoff ومرشح كان موجودًا قبله لكن أُسقط من manifest.
5. حدد المصطلحات/الادعاءات الجديدة أو المخالفة أو المتغيرة، ضمن المجال النشط فقط؛ الباقي يبقى تقدير أثر مؤجلًا.
6. تتبع الاعتماديات downstream؛ ما لم يثبت عدم تأثره يظل stale، لا تمنحه pass آليًا.
7. سجل القرار والمراجع والأدلة والجدولة في الحالة الوحيدة؛ لا تجعل delta سجل active_domain منافسًا.

## 4. جدول invalidation

| نوع الأثر | ما يجب مراجعته | ما لا يتغير تلقائيًا |
|---|---|---|
| نسخة SHA-256 مطابقة | R/الفهرس وعد المسارات؛ إثبات duplicate_of ثم قرار no_knowledge_change | لا زيادة مصادر مستقلة ولا استخراج جديد |
| مصدر فريد ذو مساهمات جديدة | R وT وC ثم أثر K/M وQA | لا تبقى T صالحة لأحدث نطاق بلا مراجعة |
| Claim مخالف أو تصحيح دليل | C وK وM وQA؛ T إن تأثرت التعريفات وR إن تغير النطاق | لا حذف رأي مدعوم لصالح الأحدث |
| مرشح سابق للـcutoff مفقود | فشل اكتمال snapshot السابقة، R/T وتوابعها | لا يجوز تصنيفه وصولًا لاحقًا لتبرير إغلاق خاطئ |
| تغيير حدود catalog أو subdomain | R/T وربط كل المتأثرات بـsnapshot جديدة | لا إعادة تفسير أدلة الإغلاق التاريخية |
| مصدر لا يخص المجال | disposition مدعوم وإحالة مجاله ومراجعة أثر الثانوي | لا extraction للمجال المحال إليه إن كان pending |

الجدول حد أدنى؛ كل بوابة احتُفظ بصلاحيتها تحتاج سبب عدم الأثر ودليلًا، لا تمريرًا جماعيًا.
في duplicate المراجع يمكن استعادة صلاحية المعرفة بعد توثيق عدم التغيير؛ أثر الوصول نفسه لا يختفي من السجل.
تُحفظ البصمات القديمة، وترتبط source_revision بـ`supersedes` في metadata؛ القديم لا يُحذف ولا يُبدّل دليله.

## 5. الجدولة ومنع إعادة الفتح الصامتة

- إذا كان المجال نفسه نشطًا، يضاف العمل كدفعة delta صريحة، ويوقف بدء Masters إذا فقدت `domain_terms_complete` صلاحيتها.
- الكتاب الموجود لا يُحذف؛ يوسم نطاقه stale ويمنع ترقيته حتى مراجعة الأثر وإعادة الاختبار.
- إذا كان المجال pending، يُصنف المصدر وينسخ ثم ينتظر دوره دون Terms/Claims/Concepts/Masters.
- إذا كان المجال done ومجال آخر نشطًا، تبقى delta queued ويظهر تقادم تغطيته؛ لا يبدأ استخراجًا موازيًا.
- إعادة فتح السابق تحتاج قرارًا صريحًا من المنسق، وتوقف كل كتّاب المجال الآخر وتوثيق تعليق عمله أولًا.
- معاملة reopen تثبت `from_state`, `target_domain`, السبب، snapshot الجديدة، البوابات، المالك، وrevision والقفل الجديد.
- تظل متطلبات الانتقال إلى المجالات الجديدة على ترتيب18؛ تعليق مجال سبق فتحه ليس تصريحًا بفتح التالي.
- عند أي انتقال جديد، تراجع كل delta ذات صلة؛ الأثر غير المقيم أو المانع للإغلاق يوقف الانتقال.
- التأجيل الموثق يحدد حدود صلاحية الإغلاق القديم ولا يسمح بوصف آخر مخزون بأنه مكتمل.

## 6. دمج الدفعة وإغلاقها

1. أنشئ snapshot جديدة تشمل الأصل والزيادات والمصائر؛ لا تعرض دفعة delta وحدها كأنها المجال كله.
2. اربط سجلات القراءة السابقة ببصماتها مع إثبات صلاحيتها؛ اقرأ الزيادات دلاليًا بلا فجوات.
3. اجمع candidate terms/Claims أثناء القراءة، وراجعها دون انتظار نهاية المجال لتسجيلها.
4. أعد T على اتحاد المصادر والأقسام الكامل؛ ثم C/K/M/QA المتأثرة وفق dependency trace.
5. حدّث الفهارس والروابط والأسئلة التي تكشف الخلاف أو تغير النطاق، ثم قارن retrieval بنفس baseline.
6. سجل `old_snapshot_id`, `new_snapshot_id`, قرارات delta، نتائج البوابات، وفجوات المتابعة.
7. لا تصبح delta `resolved` حتى تحقق الأدلة أو يثبت no-impact؛ الإرجاء وحده ليس حلًا.

## 7. اختبارات الارتداد

- مصدر فريد بعد T وقبل Master → T الحالية stale، ولا يبدأ Master حتى T الجديدة.
- المصدر نفسه باسم جديد → مسار إضافي وduplicate، لا زيادة في الأدلة المستقلة.
- رأي مخالف موثق → يحتفظ بالطرفين والشروط وعدم الحسم؛ لا حذف ولا توحيد قسري.
- مرشح من قبل cutoff اكتشف متأخرًا → سجل إخفاق تغطية؛ لا تبرير snapshot القديمة بعينة أصغر.
- وصول لمجال مغلق مع مجال آخر يعمل → intake فقط، queue وstale، لا reopen صامت.
- لا هذه الأمثلة ولا نجاح فحص الوثيقة يثبتان تشغيل إعادة معالجة أو إغلاق أي مجال حقيقي.
