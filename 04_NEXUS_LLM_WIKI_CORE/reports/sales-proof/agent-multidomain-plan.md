# خطة تنفيذ مختصرة لمشروع المعرفة متعدد المجالات

## 1. الهدف والقيود

- بناء نظام معرفة فعلي قابل للاستمرار، وليس مجموعة Python Scripts أو نتيجة تجريبية؛ ويُنفَّذ العمل عبر Agents بينما ينسّق الوكيل الرئيسي ويراجع بوابات القبول فقط. هذا متسق مع طلب «شغل حقيقي» وبنية Masters المنظمة [USER_MESSAGES_SESSION_EF22.md:L157-L163، L235-L257].
- ترتيب المجالات **إلزامي وغير متوازٍ**:
  1. `sales`
  2. `outreach`
  3. `pricing_offers`
  4. `content_strategy`
- لا يبدأ أي مجال إلا بعد إغلاق المجال السابق بحالة `done` موثقة. لا توجد معالجة مسبقة للمجال التالي ولا نقل مصادره إلى مرحلة التنفيذ أثناء بقاء المجال الحالي مفتوحًا.
- لا يُستخدم Codex في التنفيذ أو التخطيط، ولا تُقدَّم مخرجات غير مكتملة على أنها نهائية [USER_MESSAGES_SESSION_EF22.md:L259-L268].

## 2. دورة المصدر: `new` → `done/<domain>/<subdomain>`

1. **الاستقبال — `new/`:** تسجيل كل مصدر بمعرّف، عنوان، تاريخ، رابط/مسار، ومجال مرشح. يبقى المصدر هنا ما لم تُحسم قابليته للمعالجة.
2. **التصنيف:** إسناد المصدر إلى المجال الحالي وإلى `subdomain` واحد، مع تسجيل سبب التصنيف وأي غموض أو تكرار.
3. **الاستخراج بواسطة Agents:** استخراج المصطلحات ثم الادعاءات مع مواضعها في المصدر، وبعدها تجميعها في Concepts.
4. **التركيب:** بناء Master للمجال/القسم من المعرفة المقبولة، مع فصل المؤكد عن المختلف عليه أو غير المكتمل.
5. **المراجعة والفهرسة:** يراجع Agent جودة الأدلة والروابط والتكرار، ويحدّث `INDEX.md` ليصف وظيفة كل ملف؛ فوجود فهرس يشرح وظيفة الملفات مطلب بنيوي صريح [USER_MESSAGES_SESSION_EF22.md:L165-L178].
6. **الإغلاق والنقل:** لا يُنقل المصدر إلا بعد نجاح البوابات الأربع أدناه، وإغلاق الملاحظات، وتسجيل الحالة. عندها فقط يصبح المسار النهائي:

   ```text
   done/<domain>/<subdomain>/
   ```

   ويمثل `done` معالجة مكتملة قابلة للمراجعة، لا مجرد قراءة المصدر.

## 3. بوابات القبول الإلزامية

### Gate T — `terms`

- لكل مصطلح: اسم قياسي، تعريف تشغيلي، مرادفات/اختصارات، نطاق، ومرجع مصدر.
- تُسجّل المصطلحات المكررة أو المتعارضة بدل دمجها تخمينيًا.
- لا يُسمح بالانتقال إلى الادعاءات مع وجود مصطلحات جوهرية بلا تعريف أو مرجع.

### Gate C — `claims`

- تفكيك كل claim مهم إلى صياغة ذرية قابلة للفحص.
- إرفاق اقتباس/موضع المصدر، نوع الدليل، درجة الثقة، وحالة التعارض أو التأييد.
- يُحجز كل claim غير مدعوم أو متعارض في قائمة مفتوحة ولا يدخل Master النهائي.

### Gate K — `concepts`

- ربط المصطلحات والادعاءات في Concepts ذات اسم ونطاق وحدود وعلاقات واضحة.
- توثيق ما يندرج داخل المفهوم وما يقع خارجه، وربط كل مفهوم بأدلته.
- لا يُغلق المجال مع Concepts تجريبية أو غير قابلة للتتبع؛ نقاط الخلاف تبقى معلّمة بوضوح.

### Gate M — `master`

- بناء Master نهائي منظم: تعريف المجال، تصنيفاته، أنواعه وأقسامه، طرقه، الآراء/الخلافات، الأدلة، القيود، وروابط المصطلحات والـConcepts.
- للمجال الكبير Masters متعددة حسب الأقسام؛ وتُجمع الأقسام الصغيرة فقط عندما يكون ذلك موثقًا في الفهرس، بدل فرض Master واحد مسطح [USER_MESSAGES_SESSION_EF22.md:L204-L208].
- يمر Master بمراجعة اكتمال وتتبّع: لا claim بلا دليل، لا رابط مكسور، لا قسم بلا حالة، و`INDEX.md` يصف كل ملف.

## 4. تسلسل التنفيذ حسب المجال

### المرحلة 1 — `sales`

- فتح `new/` للمصادر الخاصة بالمبيعات وتصنيفها إلى subdomains عملية (مثل: prospecting، discovery، qualification، objections، closing، follow-up، operations) بعد فحص المصدر.
- تشغيل دورة `terms → claims → concepts → master` لكل subdomain.
- إغلاق جميع subdomains، تحديث فهرس المجال، ثم اعتماد `sales = done`.

### المرحلة 2 — `outreach`

- لا تُفتح قبل اعتماد `sales = done`.
- معالجة subdomains الخاصة بالوصول والتواصل (مثل: channels، targeting، personalization، sequences، measurement) بنفس البوابات الأربع.
- اعتماد `outreach = done` فقط بعد اكتمال Masters والفهرس وإغلاق التعارضات.

### المرحلة 3 — `pricing_offers`

- لا تُفتح قبل اعتماد `outreach = done`.
- معالجة subdomains مثل: value metric، packaging، pricing، discounts، guarantees، offer design، مع ربط كل claim بمصدره.
- بعد Gate M ومراجعة المجال: اعتماد `pricing_offers = done`.

### المرحلة 4 — `content_strategy`

- لا تُفتح قبل اعتماد `pricing_offers = done`.
- معالجة subdomains مثل: audience، positioning، content pillars، formats، distribution، calendar، measurement.
- إغلاق المجال بعد اكتمال Masters والفهرس ومراجعة عدم وجود معرفة غير مدعومة.

## 5. أدوار Agents وبوابة الانتقال

- **Orchestrator:** يوزّع العمل، يمنع تشغيل المجال التالي، ويعرض الحالة؛ لا يكتب المعرفة بالجملة بدل Agents.
- **Intake/Classify Agent:** يسجل المصدر ويقترح المجال وsubdomain.
- **Terms Agent ثم Claims Agent ثم Concepts Agent ثم Master Agent:** ينفذون البوابات بالتتابع، وكل Agent يسلّم مخرجه القابل للتتبع للذي يليه.
- **QA/Index Agent:** يتحقق من الأدلة، الروابط، الفهرس، والتعارضات ويصدر قرار القبول أو الإرجاع.
- **شرط فتح المجال التالي:** `current_domain == done`، وجميع مصادره ليست في `new` أو قيد المراجعة، والبوابات T/C/K/M ناجحة، والفهرس محدث، ولا توجد ملاحظات حرجة مفتوحة. أي فشل يعيد العنصر إلى مرحلته ولا يفتح المجال التالي.

## 6. مخرجات التحقق لكل مجال

- سجل مصادر يبين من `new/` إلى `done/<domain>/<subdomain>/`.
- ملفات terms وclaims وconcepts قابلة للتتبع إلى مواضع المصدر.
- Master أو Masters نهائية وفهرس يشرح وظيفة كل ملف.
- تقرير QA يوضح البوابات الأربع، المرفوضات، التعارضات، وما بقي مفتوحًا.
- سجل إغلاق صريح للمجال قبل السماح ببدء المجال التالي. هذه الخطة تحسم نقاط التشغيل التي تركتها الرسائل الأصلية مفتوحة، خصوصًا قواعد النقل وبوابات terms/Concepts وMaster [USER_MESSAGES_SESSION_EF22.md:L270-L280]، ولا تنسبها إلى متطلبات تاريخية غير مذكورة.
