# 04 — بروتوكول المراجعة والتصحيح

## الغرض

تختبر هذه المراجعة المخرج بصورة مستقلة قبل اعتماده، وتفصل بين `PASS` و`RETURN`،
وتصحح الخطأ دون محوه أو إخفاء فشل الأداة. لا يكفي أن يراجع المؤلف نصه أو أن يرسل
العامل رسالة «تم».

المرجع العام للحقول هو [SCHEMA](../SCHEMA.md)، ولعقد التسليم [نظام تنفيذ الوكيل](../systems/11_AGENT_EXECUTION_CONTRACT.md)،
وللفهارس والروابط [عقد فهارس المجلدات](../systems/17_FOLDER_INDEX_CONTRACT.md).

## 1. استقلال المراجع

المراجع:

1. يقرأ متطلبات المهمة ومسار المنتج المصرح به.
2. يفتح المنتج نفسه، لا ملخص المؤلف فقط.
3. يعيد الوصول إلى المصدر والموضع أو يشغّل فحصًا مستقلًا.
4. يقارن الادعاء بالاقتباس والسياق، ويبحث عن ما حُذف أو عُمّم.
5. يكتب حكمًا مع أدلة، حتى إذا كان الحكم `RETURN`.

إذا كان المراجع هو المؤلف نفسه ولا توجد مراجعة مستقلة ممكنة، سجّل ذلك، ولا تصف الحالة
بـQA مستقل.

## 2. قائمة الفحص

### أ. النطاق والملكية

- هل كل ملف معدل داخل `allowed_write_paths`؟
- هل بقي `raw/` وملفات الحظر دون تغيير؟
- هل المخرج يخص المجال والـsnapshot والدفعة المطلوبة؟

### ب. اختبار الاقتباس

- هل `source_id` والمسار صالحان؟
- هل locator يعود إلى النص الصحيح في view الصحيحة؟
- هل الاقتباس حرفي عند وسمه `direct_quote`؟
- هل `quote_hash` و`quote_offset` قابلان لإعادة الحساب؟
- هل السياق يغير معنى الجملة؟
- هل `what_it_does_not_prove` يمنع التعميم أو السببية الزائدة؟

### ج. نوع الدليل والثقة

- هل فُصل `reported_result` عن حقيقة مستقلة؟
- هل المثال موسوم ولا يُستخدم كقاعدة؟
- هل الاستنتاج أو الفرضية معلّمان ولا يبدوان اقتباسًا؟
- هل درجة الثقة والحالة متناسبتان مع الدليل؟

### د. التناقضات والفجوات

- هل توجد مصادر أو Claims تخالف النص أو شروطه؟
- هل حُفظ الطرفان وعلاقة `contradicts` بدل حذف أحدهما؟
- هل توجد `unread_ranges` أو أدوات فشلت ولم تظهر في النص النهائي؟

### هـ. الروابط والمسارات

- هل كل رابط Markdown إلى systems أو SCHEMA أو مصدر نسبي ويحل إلى ملف موجود؟
- هل مسارات `source_ref` و`claim_ref` و`concept_ref` تشير إلى مخرجات فعلية؟
- هل الفهرس يشير إلى الملف الصحيح دون ادعاء حالة غير مقاسة؟

### و. schema والتسلسل

- هل الحقول المطلوبة والأعداد والقيم enum صحيحة؟
- هل Claim لديه مصدر وموضع قبل `reviewed` أو `accepted`؟
- هل Concept مبني على Claims واضحة؟
- هل Master جديد يتبع بوابة T الشاملة، أم بقي `draft/partial`؟

## 3. التصنيف: PASS أو RETURN

### `PASS`

يُستخدم فقط عندما يمر المخرج بالنطاق، والاقتباس، والروابط، وschema، والحدود، ولا توجد
فجوة حاسمة غير معلّمة. يجب إرفاق أمر/اختبار أو مراجعة قابلة لإعادة الفحص، واسم
المراجع وتاريخها.

### `RETURN`

يُستخدم عند أي عيب يمنع الاعتماد أو يحتاج تعديلًا: اقتباس لا يطابق، رابط ميت، حالة
غير صحيحة، تعميم من مثال، تعارض مخفي، ملف خارج الملكية، أو اختبار لم يُنفذ. اكتب
`reason_code` وموضع الفشل والإصلاح المطلوب. لا تحوّل `RETURN` إلى `PASS` بمجرد أن
يعد المؤلف بالإصلاح.

قد يذكر التقرير `blocked` أو `partial` كحالة تشغيلية، لكن قرار المراجعة نفسه يظل
`RETURN` إذا لم تتوافر أدلة PASS.

## 4. التصحيح دون إخفاء الفشل

1. احفظ أثر الفشل: الأمر، والexit code، والموضع، وسبب العيب.
2. عدّل أصغر ملف وأصغر سطر داخل الملكية المسموح بها، أو أعد المهمة إلى مالكها.
3. لا تحذف Claim أو تعارضًا كي يمر الفحص؛ صحح الصياغة أو علّمه أو اربطه.
4. أعد فحص الجزء المصحح ثم أعد الفحص الكامل ذي الصلة.
5. اربط الإصلاح بالمراجعة السابقة، وسجّل ما لم يُعاد فحصه.

إذا فشلت الأداة نفسها، لا تستبدل «الأداة فشلت» بعبارة «الفحص ناجح». استخدم فحصًا
بديلًا محدودًا فقط إذا كان مكافئًا ومذكورًا، وإلا فالحالة `RETURN` أو `blocked`.

## نموذج مراجعة مختصر

```text
REVIEW_ID: REVIEW_example_001
المنتج: model_protocols/03_WRITING_PROTOCOL.md
المراجع: <معرّف المراجع>
النطاق: <المسارات والمرجع>
اختبار الاقتباس: PASS | RETURN | غير منطبق — <الدليل>
الروابط: PASS | RETURN — <الأمر والنتيجة>
schema: PASS | RETURN — <الحقل/الموضع>
التناقضات والحدود: <ملاحظات>
القرار: PASS | RETURN
reason_code: <لا يوجد أو رمز محدد>
الخطوة التالية: <إغلاق أو إصلاح وإعادة فحص>
```

## مثال محايد صغير

إذا كتب Claim «الطريقة تنجح دائمًا» بينما المصدر يقول «نجحت في تجربة واحدة»، فالحكم
`RETURN`: الاقتباس لا يسند التعميم. الإصلاح هو تخفيف Claim إلى نتيجة منسوبة محدودة،
وحفظ ما لا يثبته، ثم إعادة اختبار citation. حذف كلمة «دائمًا» دون تسجيل سبب التصحيح
ليس مراجعة شفافة.

## ما يثبت الإجراء

- مراجعة أعاد فيها شخص/عملية مستقلة فتح المنتج والمصدر أو تشغيل فحص موثق.
- نتائج منفصلة لاختبار الاقتباس، والتناقضات، والروابط، وschema، والملكية.
- قرار `PASS` أو `RETURN` مع reason code/أدلة/تاريخ ومراجع، وإعادة فحص بعد الإصلاح.

## ما لا يثبته الإجراء

- مرور فحص واحد لا يثبت اكتمال المراجعة الدلالية أو صحة كل Claim.
- `PASS` لمخرج واحد لا يرفع حالة المجال أو المصدر أو Master تلقائيًا.
- إصلاح النص دون أثر فشل لا يثبت أن المشكلة عولجت بطريقة قابلة للتدقيق.
- استقلال المراجع لا يثبت صحة المصدر الخارجي أو قابلية النتيجة للتعميم.

## ما يجب تسجيله

- هوية المراجع واستقلاله، ومجال المراجعة، والنسخة/البصمة أو التاريخ.
- كل فحص وأمر وexit code، والمواضع الفاشلة، وreason code، وحالة القرار.
- التناقضات والروابط الميتة وفجوات القراءة، وما عُدّل وما بقي دون إعادة فحص.
- علاقة المراجعة بالإصلاح وبأي checkpoint أو handoff لاحق.
