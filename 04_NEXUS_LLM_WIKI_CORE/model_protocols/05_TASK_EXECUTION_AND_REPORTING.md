# 05 — بروتوكول تنفيذ المهمة والتقرير

## الغرض

يوحّد هذا البروتوكول اختيار الدور، وتقسيم العمل، والملكية، والتقارير، وcheckpoints،
وhandoff، وإدارة فشل الأدوات. هو model-agnostic: لا يفترض عددًا أو اسمًا معينًا من
النماذج، ولا يسمح بإعلان النجاح اعتمادًا على رسالة Agent وحدها.

المرجع الحاكم للصلاحيات والتسليم هو [عقد تنفيذ الوكيل](../systems/11_AGENT_EXECUTION_CONTRACT.md)،
والمرجع للأدوار والتسلسل والقفل هو [التشغيل التسلسلي](../systems/16_SEQUENTIAL_AGENT_ORCHESTRATION.md).

## 1. اختيار Agent أو الدور

اختر **وظيفة** تناسب المخرج لا نموذجًا تزعم أنه «أذكى»:

| الدور | مناسب لـ | لا يملك تلقائيًا |
|---|---|---|
| المنسق | النطاق، snapshot، الملكية، القفل، وتوزيع العمل | اعتماد المعرفة بلا مراجعة |
| intake/classifier | الجرد، dedup، التوجيه والنسخة المرجعية | استخراج معرفة من مجال `pending` |
| reader/extractor | segments، Terms، وClaims مرشحة من دفعة صريحة | اعتماد Claim أو فتح Master |
| reviewer | مطابقة الدليل، الحالات، الخلافات، وقرار كل وحدة | توسيع نطاقه أو حذف الفجوات |
| concept author | توليف Claims مراجعة إلى Concept | اختراع دليل أو تجاوز T لـMaster |
| master author | Master بعد الشهادة والبوابات واختبارات الاسترجاع | تغيير الحالة العامة أو إغلاق المجال وحده |
| QA/index | فحص مستقل وفهارس وقرار hold/pass | توسيع صلاحيات الكتابة أو إنقاذ مخرج ناقص |

إذا لم توجد صلاحية أو مراجع مستقل أو مسار كتابة واضح، الحالة `blocked`؛ لا يعوضها
اختيار Agent آخر.

## 2. عقد التكليف قبل البدء

يجب أن يحتوي التكليف على الأقل على:

```yaml
run_id: RUN_...
role: reader|reviewer|...
domain: <domain أو global_intake>
snapshot_id: SNAP_...
batch_id: BATCH_...
source_ids: [SRC_...]
segments: [<حدود صريحة أو "كل المصدر">]
allowed_read_paths: [<مسارات>]
allowed_write_paths: [<مسارات>]
expected_state_revision: <رقم أو null عند عدم انطباق الحالة>
fencing_token: <رمز أو null>
acceptance_criteria: [<معايير قابلة للفحص>]
```

لا تُخترع قيمة غير معروفة؛ استخدم `null` أو اذكر أن الحقل غير منطبق، مع سبب. صلاحية
القراءة لا تمنح الكتابة، و`route_done` لا يساوي `source_done`.

## 3. تقسيم العمل والملكية

قسّم المهمة إلى وحدات يمكن التحقق منها: مصدر/segment، سجل، ملف، أو مجموعة روابط.
لكل وحدة مالك واحد في وقت الكتابة. إذا توازت دفعات داخل المجال النشط، افصل ملفاتها
وسجلاتها، ولا تكتب ملفًا مشتركًا بالتزامن دون قفل أو تنسيق.

لكل وحدة حد أدنى من الملكية:

- **المدخل:** مسار/معرّف وبصمة أو snapshot.
- **المخرج:** مسار دقيق وschema/قالب متوقع.
- **الحدود:** ما لا يلمسه العامل، وخصوصًا `raw/` والملفات خارج المهمة.
- **المراجع:** من سيعيد الفحص، ومتى، وبأي معيار.

لا يُسمح للعامل بتوسيع المهمة لأن ملفًا قريبًا يبدو مفيدًا. سجّل اقتراح التوسيع
للقائد أو أعده `RETURN`.

## 4. Checkpoint قابل للاستئناف

بعد كل وحدة أو قبل التوقف، سجّل:

- `run_id` وrole وdomain وsnapshot وbatch.
- آخر segment أو ملف اكتمل فحصه، مع locator أو بصمة مناسبة.
- المخرجات الموجودة وحالتها: مكتمل/مرشح/فشل/غير مفحوص.
- الأمر أو الأداة والنتيجة وexit code والزمن عند انطباقها.
- الفجوات، وسبب التوقف، والخطوة التالية الآمنة.

EOF أو انتهاء الجلسة لا يساوي checkpoint ولا إغلاقًا. عند الاستئناف أعد فحص المدخلات
والبصمات وdelta والملفات الجزئية، ولا تعِد التشغيل الأعمى.

## 5. Handoff

يكتب التسليم التالي بصيغة يمكن لفاعل آخر تنفيذها دون سؤال شفهي:

```text
HANDOFF: HANDOFF_<id>
الهدف والنطاق: <...>
المالك السابق/التالي: <...>
آخر دليل مثبت: <مسار + locator/بصمة + أمر ونتيجة>
المخرجات: <مسارات دقيقة وحالاتها>
غير المكتمل: <فجوات/تعارضات/أدوات فاشلة>
القيود: <لا تلمس ...؛ لا ترفع الحالة ...>
الخطوة التالية: <إجراء واحد قابل للتنفيذ>
معيار الإغلاق: <اختبار/مراجعة مطلوبة>
```

لا يحوّل handoff الحالة إلى `PASS`؛ هو تاريخ وتسليم، والمالك التالي يعيد التحقق.

## 6. فشل الأدوات وإعادة المحاولة

عند فشل أداة:

1. سجّل الأمر، والمسار/المدخل، والexit code، ورسالة الخطأ، والوقت.
2. صنّف الفشل: صلاحية، مسار، مدخل تالف، أداة غير متاحة، timeout، أو فشل دلالي.
3. أعد المحاولة بحد واضح إذا كان السبب عابرًا؛ لا تكرر بلا نهاية.
4. استخدم بديلًا فقط إذا كان ضمن الصلاحية ويقيس نفس الخاصية تقريبًا، وسجّل الفرق.
5. إذا بقيت الخاصية غير مثبتة، ارفع `blocked` أو `partial` أو `RETURN`، ولا تكتب «نجح».

فشل أداة فهرسة لا يثبت فشل المصدر، ونجاح parser لا يثبت صحة التفسير. افصل دائمًا
ما قيس عن ما استنتجته.

## 7. التقرير النهائي

كل تقرير Worker يجب أن يذكر:

1. الملفات المضافة/المعدلة ومساراتها الدقيقة.
2. ملخص التغيير وعلاقته بالتكليف.
3. المدخلات التي قُرئت فعليًا، والملفات التي لم تُقرأ أو تعذر فتحها.
4. schema/الروابط/الحقول التي أضيفت أو تحققت، عند انطباقها.
5. أوامر الاختبار أو الفحص، stdout المختصر، exit code، والزمن عند توفره.
6. ما ثبت، وما لا يثبت، والفجوات، وproblem_id أو reason code.
7. checkpoint أو handoff التالي، مع فصل نتيجة العامل عن قرار القائد.

صياغة «نجح» لا تُستخدم إلا إذا كان هناك معيار قبول وفحص فعلي يدعمه. الأفضل استخدام
«اجتاز الفحص X» أو «لم يُفحص Y» بصراحة.

## مثال محايد صغير

مهمة: مراجعة ثلاثة Claims في دفعة واحدة.

- يملك `reader` ملفات المرشحين فقط، ويملك `reviewer` قرار المطابقة، ولا يكتب الاثنان
  السجل نفسه بالتزامن.
- عند فشل فحص hash لاقتباس واحد، يسجل `RETURN` لذلك السجل، ويترك السجلين الآخرين
  بنتائج مستقلة.
- يرسل العامل تقريرًا يذكر ثلاثة مخرجات، واحدًا `RETURN`، وأمر الفحص وexit code؛
  لا يعلن أن الدفعة كلها ناجحة.

## ما يثبت الإجراء

- عقد تكليف يحدد الدور، النطاق، الملكية، المسارات، الحالة/القفل، ومعايير القبول.
- تقسيم لا يتداخل، checkpoints وhandoff قابلة لإعادة التشغيل، وتقارير بأوامر فعلية.
- إدارة فشل صريحة، ومراجعة المنتج نفسه قبل أي PASS أو انتقال حالة.

## ما لا يثبته الإجراء

- اختيار Agent أو إتمامه لرسالة لا يثبت صحة المخرج أو اكتمال المهمة.
- checkpoint يثبت آخر نقطة معروفة فقط؛ لا يثبت ما بعد تلك النقطة.
- نجاح أداة أو exit code صفر لا يثبت الفهم الدلالي أو قبول schema الكامل.
- تسليم عامل واحد لا يغير `config/processing_order.json` ولا يغلق المجال وحده.

## ما يجب تسجيله

- `run_id`, `role`, `domain`, `snapshot_id`, `batch_id`, `source_ids`، وحدود segments.
- `allowed_read_paths`, `allowed_write_paths`, revision/token، والمالك الحالي لكل ملف.
- كل checkpoint وhandoff، وآخر موضع مثبت، والمخرجات وحالاتها، والفجوات والخطوة التالية.
- أوامر الأدوات وexit codes وإعادة المحاولة، وقرار المراجع أو القائد منفصلًا عن تقرير العامل.
